# 编写技术方案

产出一份可以直接交给 `phased-dev-loop` 开发的技术方案：方案里的开发计划就是开发时的进度清单，开发过程中只在方案里打标记，不另建进度文件。

- 文档模板：`templates/tech-design.md`
- 开发计划格式：`references/plan-format.md`（phased-dev-loop 的 Stop hook 按这个格式读进度，必须遵守）

## 流程

### 1. 弄清需求

- 读用户给的需求文档、工单或对话里的描述。
- 列出需求里含糊或缺失的地方。能从代码或文档里查清楚的自己查；查不清、且会影响设计的，写进“待确认问题”，一次性问用户，不要逐条来回问。

### 2. 了解现状

- 找出需求涉及的模块、关键类、接口、表结构、调用关系。
- 涉及的代码范围大时，把代码探索交给子 agent，只把结论（模块职责、关键文件路径、现有约束）带回来。
- “现状分析”里引用具体文件路径，开发时可以直接定位。

### 3. 设计方案

- 先定整体思路，再写数据模型、接口、关键流程。
- 有多个可行做法时，选一个并在“备选方案”里写明为什么不选其他的；会明显影响成本或用户体验的选择，放进“待确认问题”让用户决定。
- 写清“本次不做”的内容，开发时以此为边界。

### 4. 拆开发计划

按下面的原则拆阶段，写进“开发计划”章节：

- **按依赖顺序排**：后面的阶段只依赖前面的阶段，不依赖后面的。一般顺序是数据模型 → 核心逻辑 → 接口 → 调用方/前端 → 监控与开关。
- **每个阶段能单独验证**：做完后能跑测试、构建或某个检查确认它是对的，不需要等后面的阶段。
- **粒度适中**：一个阶段集中在一个模块或一条完整链路上，改动量在一轮开发能完成的范围内。跨多个模块的大功能拆成多个阶段。
- **完成标准写成能执行的检查**：写具体命令或检查项（如 `mvn -pl order-service test` 通过、`POST /refunds` 返回 201），不写“功能正常”“开发完成”这类判断不了的话。
- **测试跟着阶段走**：每个阶段的测试放在本阶段里，不单独留一个“最后补测试”的阶段。

格式严格按 `references/plan-format.md`：阶段写成顶层列表项 `- [ ] 阶段N：<名称>`，涉及模块、内容、完成标准写成缩进两格的子项。不要把阶段写成 `### [ ]` 标题，标题里的复选框在 Markdown 里渲染不出来。

### 5. 定稿

- 文档开头的开发状态写 `开发状态: TODO`。开发开始时由 phased-dev-loop 改成 RUNNING。
- 用下面的自检清单检查一遍。
- 有“待确认问题”时，把问题列给用户，等确认后更新方案并清空该节。
- 告诉用户方案路径，以及开发时可以直接说“用 phased-dev-loop 按 <方案路径> 开发”。

## 文档位置

优先沿用项目已有的方案目录和命名习惯（先找找 `docs/`、`design/` 等目录下有没有已有方案）。项目里没有先例时，放在 `docs/design/<YYYY-MM-DD>-<需求简称>.md`。

## 自检清单

- [ ] 开发状态行存在，值为 `TODO`
- [ ] 开发计划章节标题包含“开发计划”，阶段都是顶层列表项 `- [ ] 阶段N：…`，子项缩进两格
- [ ] 每个阶段都有涉及模块、内容、可执行的完成标准
- [ ] 阶段顺序满足依赖关系，没有“最后统一补测试”的阶段
- [ ] 本次不做的内容已写明
- [ ] 待确认问题已全部问过用户，或明确写“无”

## 方案已经存在时

用户要求修改或补充已有方案时，只改相关部分，保持模板结构。开发状态已经是 RUNNING 的方案，不改已经标 `[x]` 的阶段；新增内容作为新的 `[ ]` 阶段加到开发计划末尾，并告诉用户。
