# 分阶段开发循环

目标：拿到一份分阶段的技术方案后，一次把所有阶段开发完，中途不停下来问“是否继续”，每完成一个阶段都在技术方案里标记并写下验证记录。

整个循环靠三样东西撑住：

1. **技术方案文档**：开发计划写在里面，进度也直接标在里面，是唯一可信的状态来源。对话被压缩、会话中断后，读它就能恢复。
2. **单轮流程**：每一轮只做一个阶段，做完必须先在方案里标记再往下走。
3. **Stop hook**（`scripts/stop_guard.py`）：方案的开发状态为 `RUNNING` 且还有未完成阶段时，拦截停止并把下一步提示注回对话，让循环自动继续。

方案由 `tech-design` skill 编写，开发计划的格式见 `~/.claude/skills/tech-design/references/plan-format.md`。

## 第 0 步：启动或恢复

项目根目录下的 `.claude/dev-loop/ACTIVE` 每行记录一份正在开发的技术方案路径（相对项目根目录）。同一项目里可以有多个会话各自开发一份方案，Stop hook 按本会话记录里最后提到的那份方案判断，所以开始干活前一定要读一遍自己的方案。

先确定本次要开发的方案：用户给了路径或说了需求名就用那份；没说时，`ACTIVE` 里只有一份 RUNNING / BLOCKED 的方案就用它，有多份就列给用户选。然后：

- **方案在 `ACTIVE` 里，开发状态为 RUNNING / BLOCKED** → 这是恢复。读方案的开发计划，从 `[~]` 阶段（没有则从第一个 `[ ]` 阶段）继续。BLOCKED 时先确认用户已经给出了需要的决定，再把开发状态改回 RUNNING。
- **方案不在 `ACTIVE` 里，或者已经是 DONE** → 这是新需求，按下面初始化：
  1. 找到技术方案文档（用户给的路径，或在对话里找）。读完整份方案，不要只读第一个阶段。还没有技术方案时，先用 `tech-design` skill 写方案，用户确认后再开始。
  2. 检查开发计划是否符合上面的格式文档：
     - 已经符合 → 不改动。
     - 阶段已经列出但没有复选框 → 改成顶层列表项 `- [ ] 阶段N：…`（原来是标题的也改成列表项），阶段内容和顺序保持不变，详情写成缩进的子项。
     - 缺少完成标准的阶段 → 在该阶段下补一个缩进子项，写能用命令或检查项判断的完成标准。
     - 方案完全没有拆阶段，或某个阶段明显超出一轮能完成的量 → 这是改动方案内容，先列出拆分建议请用户确认，确认后再写入方案。
  3. 在方案标题下加上 `开发状态: RUNNING`（已有就改成 RUNNING）。
  4. 把方案相对于项目根目录的路径追加到 `.claude/dev-loop/ACTIVE`（已有就不重复加，不要删别的行）。
  5. **直接进入第一轮**，不要停下来等用户确认。

## 单轮流程

1. **读方案的开发计划**。以文档为准，不以对话里的印象为准。
2. **选阶段**：已有 `[~]` 阶段就继续做它们。没有时找出所有**可开始的阶段**：状态是 `[ ]`，且“依赖”里的阶段都已 `[x]`（阶段没写“依赖”时，视为依赖它前面的那个阶段）。
   - 只有一个可开始的阶段 → 标成 `[~]`，自己做。
   - 有多个 → 按下面“并行开发”的规则选一组同时做，在同一次编辑里都标成 `[~]`。
3. **实现**：只做阶段范围内的改动。发现需要改前面阶段的代码时，可以改，但要在本阶段的验证记录里提一句。
4. **验证**：按阶段的“验证方式”做（见下面“验证分级”）。
   - 验证失败 → 回到第 3 步修复。同一阶段连续 3 次验证失败 → 标 `[!]`，在阶段的子项里写清卡在哪、试过什么、需要用户决定什么，把开发状态改为 `BLOCKED`，停下汇报。
5. **在方案里标记（不能跳过）**：验证通过后，在同一次编辑里完成：
   - 阶段标记改为 `[x]`
   - 在该阶段下加一个缩进子项：`  - 验证：<命令> <结果>；改动 <主要文件>`
   - 并行做的几个阶段逐个标记，每个都有自己的验证记录。
6. **立即进入下一轮**：回到第 1 步。不要输出阶段总结后结束回复，不要问“是否继续下一阶段”。阶段之间最多用一两句话说明进展。

方案里只写阶段标记和验证记录，不写调试过程，保持方案可读。

## 验证分级

每个阶段都要做**基本检查**：

- 逐条执行完成标准里的命令和检查项。
- 只跑本阶段涉及模块的测试、编译和 lint，不跑全量。全量测试留到收尾跑一次。
- 对照“编码约束”自查本阶段改动的代码。

方案里标了 `验证方式：独立` 的阶段，基本检查通过后，再派一个子 agent 独立验证：

- 让它“找理由驳回”，对照完成标准和编码约束检查本阶段的改动。
- 把已经跑过的命令和结果交给它；代码没再改动的话，它不重复跑这些测试，只补做没覆盖到的检查（边界条件、异常路径、遗漏的测试）。
- 实现者不给自己打分：独立验证提的问题要修或者写明不改的理由，不能直接忽略。

没标 `验证方式：独立` 的阶段不派子 agent 验证，整体审查放到收尾时一次做完。

## 并行开发

互相没有依赖的阶段可以同时开发，由多个子 agent 在同一个工作区里各改各的模块：

- **能放在一组的条件**：都是可开始的阶段；“涉及模块”互不重叠；一组最多 3 个。模块有重叠、或者看不出会不会改到同一批文件的，按顺序做。
- **派子 agent**：每个阶段派一个后台子 agent，自己也可以做其中一个。交给子 agent 的说明里写清：
  - 阶段的内容和完成标准，方案路径，以及“编码约束”一节；
  - 只改本阶段涉及模块里的文件；
  - 不编辑技术方案，不做任何 git 操作（commit、stash、checkout、reset 等）；
  - 只跑本模块的检查。其他模块因为别的子 agent 正在修改而编译失败时，不去修，在汇报里说明；
  - 做完汇报：改了哪些文件、跑了哪些命令、结果如何。
- **等结果**：派出后可以直接结束本轮等完成通知，Stop hook 在有后台子 agent 未交回时不会拦截。
- **合到一起验证**：这一组的子 agent 都交回后，用 `git status` 核对改动的文件有没有超出各自的模块，然后在合起来的代码上逐个阶段做验证（第 4 步），通过一个标记一个。某个阶段验证失败，就由自己按顺序修复。

## 收尾

所有阶段都是 `[x]` 后：

1. 跑一遍全量测试/构建（项目有的都跑）。
2. 整体审查：派一个子 agent 审查整个需求的改动（让它“找理由驳回”，对照方案和编码约束，只报能说清触发场景的问题），确认的问题修掉。由 `dev-flow` 调起时跳过这一步，dev-flow 的代码审查环节会做。
3. 对照方案逐条检查有没有漏掉的功能点；有遗漏就在开发计划末尾补一个 `[ ]` 阶段（并告诉用户补了什么），继续循环。
4. 全部通过后把开发状态改为 `DONE`，从 `ACTIVE` 里删掉这份方案那一行，然后向用户汇报：完成了哪些阶段、验证结果、遗留问题。

由 `dev-flow` 调起时（本需求在 `.claude/dev-flow/` 下的状态文件里环节是“开发”），改为 DONE 后不向用户汇报，直接回到 dev-flow 进入代码审查。

## 硬性规则

- **R1 不在阶段之间停下。** 还有未完成阶段且没有阻塞时，不结束回复，不征求“是否继续”。允许停下的只有三种情况：开发状态是 `DONE`；开发状态是 `BLOCKED` 且写清了需要用户决定什么；用户明确要求暂停。
- **R2 先标记，再继续。** 一个阶段验证通过后，必须先在方案里标 `[x]` 并写验证记录，再开始下一阶段。没有验证记录的阶段不能标 `[x]`。
- **R3 技术方案是唯一状态来源。** 对话被压缩、换会话、被 hook 唤醒时，第一件事都是重新读方案的开发计划。不另建进度文件。
- **R4 `[~]` 只给正在做的阶段。** 同时有多个 `[~]` 时，它们必须是按“并行开发”规则选出的同一组。
- **R5 BLOCKED 只用于必须由用户决定的事**（需求不明确、方案矛盾、需要凭据/权限、要做不可逆的操作）。能自己查清楚或有合理默认值的，自己决定并在验证记录里写明选择，不要为此停下。
- **R6 不做方案以外的事。** 发现方案外的问题，汇报时列出来，不顺手改。

## 编码约束

实现和验证阶段都要遵守。派子 agent 实现或验证时，把这一节一起交给它。

- **C1 单个方法尽量不超过 50 行**（不含注释和空行）。这是软限制：超过时按步骤拆成职责单一的子方法，方法名体现它做的那一步；逻辑紧密、拆开反而更难读的流程（比如一整套状态分支）可以略超。只约束本次新写或改动的方法，已有的超长方法不顺手重构。
- **C2 service 层不直接访问数据库。** service 里不写 SQL，不直接调用 JdbcTemplate、EntityManager、数据库连接这类底层接口，数据读写都通过 repository / DAO / mapper 层完成。项目已有的分层叫法不同时，按项目的叫法来。
- **C3 尽量减少数据库查询次数。**
  - 不在循环里查数据库。先收集需要的 ID 或条件，一次批量查出来，放进 Map 等本地结构，再在内存里做匹配和计算。
  - 同一份数据在一次请求里只查一次，后续逻辑复用查出来的结果。
  - 能用一条查询（批量 IN、关联查询）拿到的数据，不拆成多次查询。
  - 数据量可能很大时（整表、无上限的列表），分页或分批查，不要一次全部加载到内存。
- **C4 关键逻辑打日志，接口请求打参数日志。**
  - 所有接口（对外提供的接口，以及调用的外部接口）都要记录请求参数。
  - 关键逻辑要打日志：状态变化、分支判断的结果、写操作（新增、修改、删除）、调用失败和异常。
  - 日志里带上能定位问题的业务标识（如订单号、用户 ID）。
  - 密码、token、身份证号、手机号这类敏感字段要脱敏或不打；请求体很大时只打关键字段或截断。
  - 沿用项目已有的日志框架和格式，不另起一套。
- **C5 代码注释简洁，只描述代码的功能。** 不写历史、背景、修改过程（如“原来的写法有问题所以改成……”“为了配合某需求加的”），这些内容放到提交记录或技术方案里。代码本身已经能看明白的地方不写注释。

## Stop hook 的行为

hook 在 skill 被调用后生效，每次 Claude 准备结束回复时运行。hook 命令按固定路径 `~/.claude/skills/phased-dev-loop/scripts/stop_guard.py` 找脚本（hook 命令里取不到 skill 所在目录），所以 skill 必须安装在这个位置。各种情况下的行为：

| 方案情况 | hook 行为 |
| --- | --- |
| `ACTIVE` 里的方案本会话一份都没提到过（都是别的会话在开发） | 放行 |
| 本会话最后提到的那份方案开发状态不是 RUNNING | 放行 |
| 读不到会话记录，且 `ACTIVE` 里不止一份方案 | 放行（分不清是哪份） |
| 本会话还有没交回结果的后台子 agent | 放行（结果交回后会自动接着干） |
| 还有 `[ ]` / `[~]` 阶段 | 拦截，提示下一个阶段，并要求先补齐上一阶段的标记 |
| 只剩 `[!]` 阶段 | 拦截，要求继续解决或改成 BLOCKED |
| 全部 `[x]` 但开发状态仍是 RUNNING | 拦截，要求执行收尾 |
| 本会话连续 3 次拦截后方案文档都没有变化 | 放行，并提示用户检查方案，防止死循环（各会话分开计数） |

被 hook 拦截后收到的 `[phased-dev-loop]` 提示，按单轮流程处理即可，不用向用户解释。

把阶段交给后台子 agent 实现时，派出后直接结束本轮等完成通知即可，hook 不会拦截；不要为了等结果反复输出“还在等”。

需要临时让循环停下时，把方案的开发状态改成 `BLOCKED`，或从 `.claude/dev-loop/ACTIVE` 里删掉这份方案那一行。

## 节省上下文

阶段多时对话会很长。探索代码、跑测试看输出、读长日志这类工作优先交给子 agent，只把结论带回主对话。方案里已经记录了进度，不需要在对话里重复总结前面的阶段。
