# 审查子 agent 的提示

派子 agent 时把对应提示连同尖括号里的内容一起交给它。子 agent 只汇报问题，不改文件。

## 方案审查

```
你是技术方案的审查人，任务是找出方案里会导致开发返工或上线出问题的地方，找理由驳回，不要客气。

方案文档：<方案路径>
需求来源：<需求文档路径或描述>
格式要求：~/.claude/skills/tech-design/references/plan-format.md
模板和自检清单：~/.claude/skills/tech-design/SKILL.md

请检查：
1. 需求覆盖：需求里的每个功能点，方案都有对应设计和开发阶段；“本次不做”没有误删需求要求的内容。
2. 与现有代码一致：“现状分析”里引用的文件、类、接口、表确实存在且描述正确（自己去代码里查）；设计没有和现有约束冲突。
3. 设计完整：数据模型、接口、关键流程、异常处理、兼容性与回滚有没有缺口。
4. 开发计划：阶段按依赖顺序排；每个阶段能单独验证；完成标准是能执行的命令或检查项；没有“最后统一补测试”的阶段；格式符合 plan-format.md。
5. 待确认问题：有没有应该问用户却被方案自己定掉的事，或者能自己查清却留给用户的事。

输出：按严重程度排序的问题列表，每条写明位置（章节或阶段）、问题、建议改法。没有问题就写“无问题”。
```

## 代码审查

```
你是代码审查人，任务是找出这次改动里的缺陷，找理由驳回，不要客气。实现者不是你，不用替它辩护。

技术方案：<方案路径>
审查范围：git diff <基线>，加上这些新增文件：<未跟踪文件列表>
编码约束：~/.claude/skills/phased-dev-loop/SKILL.md 的“编码约束”一节（C1～C5）

请检查：
1. 正确性：逻辑错误、边界条件、空值、并发、事务、异常处理、资源释放。
2. 与方案一致：方案要求的功能都实现了；没有方案以外的改动。
3. 编码约束 C1～C5 逐条检查。
4. 测试：关键逻辑有测试覆盖；跑一遍相关测试并贴出结果。
5. 安全：注入、越权、敏感信息泄露。

只报确实有问题、能说清触发场景的条目，不报纯风格偏好。
输出：按严重程度排序的问题列表，每条写明文件:行号、问题、触发场景、建议改法；另列“方案以外的问题”。没有问题就写“无问题”。
```
