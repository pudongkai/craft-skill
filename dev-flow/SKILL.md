# 开发全流程

把各环节已有的 skill 串起来，环节之间不再需要用户手动转交。每个环节的具体做法仍以对应 skill 为准，本 skill 只负责：按顺序推进、记录当前环节、在环节交接处自动进入下一环节。

| # | 环节 | 做法 | 完成后 |
| --- | --- | --- | --- |
| 1 | 需求澄清 | 本文件 | 自动进入 2 |
| 2 | 编写方案 | `tech-design` skill（第 1～4 步） | 自动进入 3 |
| 3 | 方案自审 | 子 agent 审方案，见 `references/review-prompts.md` | 进入 4 |
| 4 | 等待确认 | 把方案和待确认问题交给用户 | **停下**，用户确认后进入 5 |
| 5 | 开发 | `phased-dev-loop` skill | 方案开发状态变成 DONE 后自动进入 6 |
| 6 | 代码审查 | 子 agent 审整个 diff，见 `references/review-prompts.md` | 自动进入 7 |
| 7 | 提交 | 本地提交，准备 PR 描述 | **停下**，用户同意后推送并建 PR，进入“完成” |

## 流程状态文件

每个需求一个状态文件 `.claude/dev-flow/<需求简称>.state`（放在项目根目录下，需求简称用英文短横线形式，如 `order-refund`），每行一个 `键: 值`。同一项目里可以有多个会话各自推进一个需求，Stop hook 按本会话记录里最后提到的那个状态文件判断，所以开始干活前一定要读一遍自己的状态文件。

```
环节: 开发
需求: <需求文档路径、工单链接，或一句话描述>
方案: docs/design/2026-11-03-order-refund.md
分支: feat/order-refund
基线: 3f2a9c1
等待用户:
审查: 第1轮 4 个问题已修复；第2轮 无问题
```

- `环节` 取值：`需求澄清`、`编写方案`、`方案自审`、`等待确认`、`开发`、`代码审查`、`提交`、`完成`、`阻塞`。
- `等待用户` 非空时表示在等用户回答或决定，Stop hook 放行；写清楚在等什么。用户回复后清空。
- `方案`、`分支`、`基线` 在对应环节产生后再填。
- 只记录环节和关键信息，不写过程。方案的阶段进度仍只记在技术方案里，由 phased-dev-loop 维护。

**每进入一个新环节，先改状态文件的 `环节`，再开始做。** 对话被压缩、换会话、被 hook 唤醒时，第一件事是读状态文件，按 `环节` 继续。

## 启动或恢复

先看 `.claude/dev-flow/` 下有没有本需求的状态文件：用户说了需求名就找对应的那个；用户只说“继续开发流程”时，`环节` 不是 `完成` 的状态文件只有一个就用它，有多个就列给用户选。

- 找到且 `环节` 不是 `完成` → 恢复：按 `环节` 继续；`环节` 是 `等待确认` 或 `阻塞`、`等待用户` 非空时，先确认用户已经给出需要的回答。
- 没有 → 新流程：新建 `<需求简称>.state`，写入 `环节: 需求澄清` 和 `需求`，开始环节 1。
  - 用户一上来就给了现成的技术方案 → 填好 `方案`，从环节 3 开始。
  - 方案已经确认过、用户只要求开发 → 从环节 5 开始。

## 各环节

### 1. 需求澄清

- 读需求文档、工单或对话里的描述；需要了解代码现状时交给子 agent 查，只带回结论。
- 把含糊或缺失的地方分成两类：
  - **影响整体方向的**（做不做某块功能、选哪种业务规则，答案不同方案会完全不同）→ 一次性列给用户，写 `等待用户: 需求澄清问题`，停下等回答。
  - **其余的** → 选一个合理的默认做法，带到环节 2 写进方案的“待确认问题”，在环节 4 一起确认。
- 能从代码或文档里查清楚的自己查，不问用户。
- 没有影响整体方向的问题时不停，直接进入环节 2。

### 2. 编写方案

按 `tech-design` skill 的第 1～4 步写方案，以下几点与单独使用 tech-design 时不同：

- 环节 1 已经澄清过的内容直接用，不重复问。
- tech-design 第 5 步“定稿”里“把待确认问题列给用户”“告诉用户方案路径”这两件事不在这里做，统一放到环节 4。
- 写完后把路径填进状态文件的 `方案`，进入环节 3。

### 3. 方案自审

- 派一个子 agent 按 `references/review-prompts.md` 里的“方案审查”提示审方案。实现者不给自己打分。
- 子 agent 提的问题逐条处理：确实有问题的改方案；需要用户决定的放进“待确认问题”；不认同的在交给用户时说明理由。
- 最多审两轮。第二轮仍有分歧的，放到环节 4 交给用户。

### 4. 等待确认

- 向用户汇报：方案路径、整体思路（三五句话）、开发阶段列表、自审改了什么、待确认问题（带上你的建议做法）。
- 写 `环节: 等待确认`、`等待用户: 确认方案` 后停下。
- 用户回复后：
  - 有修改意见 → 改方案，清空“待确认问题”中已确认的项，再汇报一次改了什么。改动大时重新走环节 3。
  - 确认 → 清空 `等待用户`，进入环节 5。用户说“确认”就算确认，不要再问“是否开始开发”。

### 5. 开发

1. 准备分支：当前在默认分支（main / master 等）时，新建 `feat/<需求简称>` 分支；已经在功能分支上就沿用。把分支名和当前提交写进状态文件的 `分支`、`基线`。工作区有和本需求无关的未提交改动时，不要 stash 或丢弃，记下来，提交时排除。
2. 写 `环节: 开发`，按 `phased-dev-loop` skill 开发方案里的所有阶段。开发期间由 phased-dev-loop 的 Stop hook 推动阶段循环，本 skill 的 hook 不干预。
3. phased-dev-loop 收尾、方案开发状态变成 `DONE` 后，**不要向用户汇报后结束**，直接进入环节 6。
4. 方案开发状态变成 `BLOCKED` → 写 `环节: 阻塞`、`等待用户: <要用户决定的事>`，停下汇报。用户给出决定后，改回 `环节: 开发` 继续。

### 6. 代码审查

- 审查范围：`git diff <基线>` 加上本需求新增的未跟踪文件。开发时只有标了 `验证方式：独立` 的阶段单独审过，其余阶段的审查都在这一步完成，不要省略。
- 派一个子 agent 按 `references/review-prompts.md` 里的“代码审查”提示审查，它会对照技术方案和 phased-dev-loop 的编码约束检查。
- 处理结果：
  - 确认是问题的 → 修复，跑相关测试。
  - 属于方案以外的问题 → 不改，留到最终汇报里列出。
  - 不认同的 → 在最终汇报里写明理由。
- 修复后再审一轮，最多两轮。每轮结束在状态文件的 `审查` 里记一句结果。
- 修复会改动功能时，在技术方案的开发计划末尾补一个 `[x]` 阶段并写验证记录，保持方案和代码一致。
- 审查结束后跑一遍全量测试/构建，通过后进入环节 7。

### 7. 提交

1. 看 `git log` 的提交信息风格，沿用项目习惯写提交信息。
2. 只提交本需求的改动：不提交 `.claude/dev-flow/`、`.claude/dev-loop/`，不提交环节 5 记下的无关改动。改动按阶段能清楚分开时可以按阶段分多个提交，否则提交一次。
3. 按技术方案整理 PR 描述：背景（一两句）、主要改动（按阶段）、验证结果、审查结论、遗留问题、技术方案路径。
4. 推送和建 PR 是对外操作，必须先问用户：汇报提交列表和 PR 描述，写 `等待用户: 确认推送并创建 PR` 后停下。
5. 用户同意后 `git push -u origin <分支>`，用 `gh pr create` 建 PR（项目有 PR 模板时按模板填）。用户说不需要 PR 就跳过。
6. 写 `环节: 完成`，清空 `等待用户`，向用户做最终汇报：PR 链接、完成的阶段、审查结论、遗留问题。

## 硬性规则

- **R1 环节之间不停下。** 一个环节完成后直接进入下一个，不输出总结后结束回复，不问“是否进入下一环节”。允许停下的只有：`环节` 是 `等待确认`、`阻塞` 或 `完成`；`等待用户` 已写明在等什么；用户明确要求暂停。
- **R2 先改状态文件，再做事。** 进入新环节、开始等用户、用户回复后，都先更新状态文件。
- **R3 状态以文件为准。** 环节看状态文件，阶段进度看技术方案，不以对话里的印象为准。
- **R4 对外操作先问。** 推送、建 PR、发消息、改共享环境这类操作，必须用户同意后才做。本地建分支、本地提交不用问。
- **R5 只在必须时问用户。** 能查清楚或有合理默认值的自己决定，在方案或汇报里写明选择。
- **R6 各环节的规则照旧。** tech-design 的格式要求、phased-dev-loop 的硬性规则和编码约束在本流程里同样适用。

## Stop hook 的行为

hook 在 skill 被调用后生效，按固定路径 `~/.claude/skills/dev-flow/scripts/flow_guard.py` 找脚本，所以 skill 必须安装在这个位置。脚本复用 phased-dev-loop 的 `stop_guard.py`，两个 skill 要装在同一个 skills 目录下。

| 情况 | hook 行为 |
| --- | --- |
| 本会话没提到过任何状态文件（都是别的会话的需求），或 `环节` 是 `等待确认` / `阻塞` / `完成` | 放行 |
| `等待用户` 非空 | 放行 |
| 本会话还有没交回结果的后台子 agent | 放行（结果交回后会自动接着干） |
| `环节` 是 `开发`，方案开发状态不是 `DONE` | 放行（由 phased-dev-loop 的 hook 负责） |
| `环节` 是 `开发`，方案开发状态是 `DONE` | 拦截，要求进入代码审查 |
| 其他环节 | 拦截，提示继续当前环节或进入下一环节 |
| 本会话连续 3 次拦截后状态文件和方案都没有变化 | 放行，并提示用户检查，防止死循环（各会话分开计数） |

被 hook 拦截后收到的 `[dev-flow]` 提示，按对应环节处理即可，不用向用户解释。

需要临时让流程停下时，在状态文件里写 `等待用户: <原因>`，或删除这个状态文件。

## 节省上下文

整个流程对话会很长。查代码、审查、跑测试看输出这类工作优先交给子 agent，只把结论带回主对话。状态文件和技术方案里已经记录了进度，不需要在对话里重复总结前面的环节。
