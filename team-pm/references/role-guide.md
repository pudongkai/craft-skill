# 角色会话指南

团队角色（产品、开发、QA）处理任务单时共用的规则：领单、干活、提问、提交、交活，以及文档放在哪。看板格式、状态流转、事件这些是给 PM 看的，在同目录的 `protocol.md`，角色不用读。

看板脚本：`python3 ~/.claude/skills/team-pm/scripts/board.py <命令>`，下文简写为 `board`。

## 怎么干活

每个角色由 PM 派出，只处理一张任务单，做完就结束。派单提示里给出项目名、任务单编号和工作目录。需要时可以再派自己的子 agent，交代清楚工作目录和范围，只让它带回结论。

1. **领取**：按派单提示运行 `board item claim <项目> <编号> --resume`，它会一起打印任务单全文和项目卡，不用再 `item show`、`project show`。再读任务单“输入”里的文档。项目卡的“规模”（`S` / `M` / `L`，没有这一行按 `M`）决定按角色 skill 里哪一档的做法。
2. **干活**：按本角色 skill 做。只改本单范围内的文件。工作目录是项目专用的 worktree，不要切分支、不要动别的 worktree。
3. **遇到问题**：
   - 能从代码、文档里查清的，自己查；有合理默认做法的，自己决定，写进产出文档和“结果”。
   - 需要别的角色回答的：建一张答疑单（`board item new <项目> --role 产品 --type 答疑 --from <本单编号> --desc "<问题，附你建议的答案>"`），然后 `board item block <项目> <编号> --reason "等 <答疑单号> 答复：<问题>"`，结束。答疑单完成后 PM 会把答案 `reply` 到你的单上再派回来。
   - 自己定不了的（方向性取舍、要花钱、不可逆操作、需要凭据，或者几种做法自己拿不准）：`board item ask-human <项目> <编号> --question "<问题，附选项和你的建议>"`，结束。PM 先看：非阻塞的 PM 直接答复，只有阻塞性的才转给人。
   - **不在会话里直接问人。** 后台会话没人看着，问了也没人答。
4. **提交**：产出的文档、代码提交到项目分支。只提交自己改的文件：`git add <路径>` 后用 `git commit -m "…" -- <路径>`（同一个工作目录里可能有别的角色在并行提交，不带路径会把别人暂存的文件一起提交；不要 `git add -A`），不提交 `.claude/` 下的文件。不推送。
5. **交活**：`board item done <项目> <编号> --output "<产出路径或提交号>" --result "<三五行结论>"`，然后结束。“结果”是给 PM 看的，PM 只读这一节决定下一步：写结论、产出路径、遗留问题，不写过程。阻塞、待人确认时也在“结果”里写清在等什么、已经做到哪，重派后的会话凭它接着做。

任务单还是“进行中”时，Stop hook 会拦住停止，提示先 `done`、`block` 或 `ask-human`。

同一项目同一时间最多一张代码类单（开发、修复）在跑；文档类单可以同时跑，所以只提交自己的文件。

## 文档位置

| 文档 | 路径 | 谁写 | 登记到项目卡 |
| --- | --- | --- | --- |
| 需求文档 | `docs/prd/<项目>.md` | 产品 | `project doc <项目> 需求 <路径>` |
| 技术方案 | 沿用仓库已有方案目录，没有时 `docs/design/<日期>-<项目>.md` | 开发 | `project doc <项目> 方案 <路径>` |
| 测试计划 | `docs/test/<项目>.md` | QA | `project doc <项目> 测试计划 <路径>` |
| 测试报告 | `docs/test/<项目>-report.md` | QA | `project doc <项目> 测试报告 <路径>` |
| 验收结论 | `docs/test/<项目>-acceptance.md` | 产品 | `project doc <项目> 验收 <路径>` |

规模 `S` 的项目没有单独的需求文档和测试计划：开发写的“需求和方案”合一文档放在技术方案的位置，登记为“方案”，验收标准就写在里面。

需求文档、测试计划、测试报告、验收结论是过程文档，交付时由 PM 从仓库删除（原文留在 git 历史里），只有技术方案留在仓库。所以测试代码、方案等长期保留的文件不要引用这几份文档的路径。
