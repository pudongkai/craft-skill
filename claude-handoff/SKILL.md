# Claude 接力

把当前任务交给另一台 Mac 上的 Claude。两台 Mac 互相都可以接力。

脚本（相对本技能目录，运行前拼成绝对路径）：

- `scripts/peer.py`：找到对方机器并在上面执行操作，命令见文件开头的说明。`<机器>` 写电脑名的一部分即可，如 `m16`。
- 对方的看板命令：`~/.claude/skills/team-pm/scripts/board.py`，下文写作 `board`；在对方执行时用 `peer.py ssh <机器> 'python3 ~/.claude/skills/team-pm/scripts/board.py …'`。

接手的一方一律用 `team-pm` 技能推进：对方的 PM 会话立项（或导入看板上的项目），再派产品、开发、QA 角色去做。**同一个仓库的项目交给对方同一个 PM 会话**，一个仓库在对方只有一个 PM。
- `scripts/register.sh`：把本机地址登记到 iCloud 云盘，由 launchd 自动运行。
- `scripts/install.sh`：安装登记任务；`install.sh uninstall` 卸载。

## 怎么找到对方

每台 Mac 上有一个 launchd 任务，登录时、网络变化时和每隔 5 分钟，把本机的电脑名、主机名、用户名、IP 写进 `iCloud 云盘/ClaudeHandoff/hosts/<主机名>.json`。两台 Mac 登录同一个 Apple 账户，所以都能读到对方的登记。

`peer.py` 按登记的地址连过去，连上后核对主机名，对不上就不算连通。SSH 主机密钥按主机名记录，地址变了也能认出是不是同一台机器。登记很久没更新时，对方可能在睡眠、关机或换了网络，`peer.py` 会在报错里说明。

## 首次设置（每台 Mac 一次）

`peer.py list` 能列出对方、`peer.py resolve <机器>` 能连通，说明设置完成，跳过本节。否则逐项检查，需要用户在对方机器上手动做的，把命令整理好交给用户：

1. **装好技能**：craft-skill 拉到最新，`~/.claude/skills/claude-handoff` 指向仓库里的 `claude-handoff`。
2. **登记地址**：运行 `scripts/install.sh`。iCloud 云盘要开着。
3. **远程登录**：系统设置 → 通用 → 共享 → 打开“远程登录”。
4. **互相加公钥**：把本机 `~/.ssh/id_ed25519.pub`（或其他公钥）加到对方的 `~/.ssh/authorized_keys`，权限 `~/.ssh` 700、`authorized_keys` 600。双向接力时两边都要加。
5. **允许远程控制“终端”**：接力时通过 SSH 让对方的“终端”应用弹出窗口。第一次接力时对方屏幕上会弹出授权提示，要点“允许”；没点到或点了拒绝，`launch` 会报错，到对方的 系统设置 → 隐私与安全性 → 自动化 里允许 sshd-keygen-wrapper 控制“终端”。
6. **对方装好团队技能**：对方的 craft-skill 拉到最新，`~/.claude/skills/` 下有 team-pm、team-product、team-dev、team-qa、tech-design、phased-dev-loop，并运行过一次 `~/.claude/skills/team-pm/scripts/install.sh`（把角色 agent 定义链接到 `~/.claude/agents/`）。
7. **对方的 Claude Code 版本**：窗口里启动的 Claude 用的是对方终端里的 `claude`。启动后屏幕第一行会显示版本号，和本机差得太多时提醒用户，phased-dev-loop / dev-flow 的 Stop hook 在旧版本上可能不生效。

## 接力流程

### 1. 确认对方在线

`peer.py resolve <机器>`。连不上就把报错原因告诉用户，停下。

### 2. 写交接文档

在项目里写 `.claude/handoff-<YYYYMMDD>-<任务简称>.md`，让对方的 Claude 不看这段对话也能接着做：

- **目标**：要完成什么，做到什么程度算完成。
- **当前进度**：已经做完的、正在做的、还没做的。用 phased-dev-loop / dev-flow 开发时，进度以技术方案为准，这里写方案路径和当前环节，不重复列阶段。
- **关键信息**：涉及的文件、做过的决定和原因、用户提过的要求、试过但不行的做法。
- **怎么验证**：要跑的测试、构建命令或检查项。
- **项目信息**（给对方 PM 立项用）：项目名（英文短横线）、目标、优先级、哪些确认点要人确认；需求文档、技术方案的路径；按下面的对照写出建议从哪个阶段接着做：
  - 只有需求描述 → 需求；有需求文档没有方案 → 方案；
  - 方案 `方案评审: 通过`、`开发状态` 是 TODO / RUNNING / BLOCKED → 开发（RUNNING 时写明做到第几个阶段）；`DONE` → 测试。
  - 交接的是本机看板上的团队项目时，写“导入看板项目：.claude/<项目名>.tgz”，不用写上面这些。
- **要用的技能**：写“用 team-pm 技能接手推进”。原来在用 dev-flow / phased-dev-loop 的，写明当前环节或阶段，由对方 PM 派开发角色接着做。
- **分支和提交**：分支名、最后一个提交号。

只写结论，不贴大段日志和对话。

### 3. 提交并推送分支

- 只提交本任务的改动，不提交 `.claude/` 下的本地状态文件（交接文档另外复制，不走 git）。
- 推送是对外操作，先告诉用户要推送哪个分支、包含哪些提交，用户同意后再推送。
- 工作区里和本任务无关的改动不提交，也不要 stash 或丢弃，在交接文档里写明。

### 4. 在对方准备代码

1. `peer.py find-project <机器> <origin 地址>` 找到对方的仓库目录。找到多个时选和本机目录名相同的；找不到就问用户要不要克隆、放在哪。
2. `peer.py ssh <机器> 'cd <目录> && git fetch'`。只拉取，**不要在对方主目录 checkout 这个分支**：对方 PM 会给项目建单独的 worktree 检出它，分支已经在主目录检出时 worktree 会建不出来。对方本地已有同名分支时，确认它和远程一致或落后（`git -C <目录> log --oneline <分支>..origin/<分支>` 有输出、反过来没有），否则停下问用户。

### 5. 复制交接文档

`peer.py copy <机器> <本地交接文档> <对方目录>/.claude`，必要时先 `peer.py ssh <机器> 'mkdir -p <对方目录>/.claude'`。脚本会核对两边内容一致，输出“两边内容一致”才算复制成功。

### 6. 交给对方的 PM 会话

**先准备看板项目（只有本机看板上的团队项目才做）**：交接的是本机 `board` 上的项目时：
1. 等这个项目进行中的单都收尾（`board item list <项目> --status 进行中` 为空），或者停掉它们。
2. `board project export <项目> --out <项目目录>/.claude/<项目>.tgz`，和交接文档一样用 `peer.py copy` 复制到对方的 `.claude/`。
3. 本机看板上 `board project set <项目> 阶段 暂停`、`board project set <项目> 交接 "<机器> <日期>"`，本机 PM 不再推进它。

**找对方负责这个仓库的 PM 会话**：

`peer.py ssh <机器> 'python3 ~/.claude/skills/team-pm/scripts/board.py pm find --repo <对方目录>'`

- **输出终端编号**（`/dev/ttys…` 或 tmux 会话名）→ 对方已经有 PM 在管这个仓库，把提示词发给它：`peer.py send <机器> <终端编号> "<提示词>"`。脚本发完等 8 秒打印对方屏幕，确认消息已经进了对话框。
- **输出“没有”** → 新开 PM 会话：`peer.py launch <机器> <对方目录> <会话名> "<提示词>"`，然后马上登记，让后面同一个仓库的交接都发给它：
  `peer.py ssh <机器> 'python3 ~/.claude/skills/team-pm/scripts/board.py pm register --repo <对方目录> --terminal <窗口编号>'`
  对方的 PM 立项时也会自动把自己登记成这个仓库的 PM。

一次交接同一个仓库的多个任务时，每个任务一份交接文档，用一条提示词列出所有文档，只开一个 PM 会话。

**启动方式**（新开时）：
- 默认在对方弹出一个“终端”窗口运行 Claude。窗口在对方的图形界面里，能读到钥匙串里的登录信息，用户在对方屏幕上直接就能看、能操作。
- 输出里的“窗口编号”（`/dev/ttys…`）记下来，之后查看对方屏幕、往里发消息都用它。Claude 会改写窗口标题，所以不按标题找窗口。
- 会话名用 `team-pm-<仓库目录名>`，只作为窗口刚打开时的标题。
- 对方不方便弹窗口（比如没人在用、锁屏）时，加 `--tmux` 改为在对方的 tmux 里启动，这时编号就是会话名。tmux 方式要求对方本地终端里已经有 tmux 在运行（`tmux new -d -s main`），否则读不到登录信息。

**提示词**（发给已有的 PM 和新开的 PM 都用这一句，写成一行）：

`使用 team-pm 技能接手交接过来的项目：读 .claude/handoff-<…>.md（多个就逐个列出），按 team-pm 的“接手交接”一节立项或导入后推进。项目交付后删除对应的交接文档。`

**启动前检查**：确认对方装了团队技能和角色 agent：`peer.py ssh <机器> 'ls -d ~/.claude/skills/team-pm ~/.claude/skills/team-dev ~/.claude/agents/team-dev.md'`。缺了就停下告诉用户；对方的 craft-skill 不是最新时，也先告诉用户，用户同意后再在对方 `git pull` 并运行 `install.sh`。

新开时脚本启动后等 15 秒，打印对方屏幕的最后几行。看到没登录、询问是否信任目录等提示时，按提示告诉用户怎么处理。

### 7. 清理本机的交接文档

第 5 步确认复制成功、第 6 步消息已经进了对方 PM 的对话框（或新开的 Claude 正常启动，屏幕上没有未登录、没有等待确认信任目录）后，删除本机的交接文档和导出的 `.tgz`，以对方那份为准。任一步没成功就保留，用户可能要在本机接着做。

对方那份由接手的 PM 在项目交付后删除（见第 6 步的提示词）。不在读完后立刻删，因为对方的对话被压缩后还要重新读它。

### 8. 告诉用户

- 交给了哪台机器、哪个目录、哪个分支；交给了对方已有的 PM 会话还是新开的；本机的交接文档是否已删除。
- 在对方机器上查看进度：直接看弹出的终端窗口；用 `--tmux` 启动的，执行 `tmux attach -t <会话名>`（看完按 `Ctrl-b d` 退出，不会打断它）。
- 本机这边之后不要再改同一个分支，避免两边冲突。

用户之后问进度时，用 `peer.py screen <机器> <窗口编号>` 看对方屏幕的最后 40 行。

## 注意

- 两台 Mac 要在能互相连通的网络里。公司网络如果屏蔽了设备之间的连接，登记了地址也连不上。
- 不在对方机器上做设置以外的改动：不删文件、不改配置、不处理对方未提交的改动。
- 卸载：每台 Mac 上运行 `scripts/install.sh uninstall`。
